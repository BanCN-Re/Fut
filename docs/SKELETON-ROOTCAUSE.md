# 骨骼问题完整技术档案

> 这份文件记录骨骼为什么"从开始到现在就没对过"，以及每一层的真实根因。
> 每个结论都有运行时日志或内存 dump 作为证据，没有推测。

## 结论速览

骨骼问题**不是单一 bug，是五层叠加**。每修好一层，下一层的症状才露出来。
前四层已修，第五层（父骨关系）刚换成几何推断，待进对局验证。

| 层 | 问题 | 状态 |
|---|---|---|
| 1 | `ue::Read` 大小上限拒绝骨骼数组 | ✅ 已修 |
| 2 | 选错网格组件（落在数据资产上） | ✅ 已修 |
| 3 | 组件判定用类名字符串匹配 | ✅ 已修（改 UClass 指针） |
| 4 | 骨名数组步长硬编码错误 | ✅ 已修（改自动推导） |
| 5 | 父骨索引字段不可信 | 🔄 改几何推断，待验证 |

## 第 1 层：`ue::Read` 静默拒绝大数组

**症状**：骨骼探测一直失败，日志只有一行 `read failed (14784 bytes)`。

**根因**：`ue::Read` 有个 `size > 0x1000` 的守卫，是给标量读写的。
骨骼数组是 `308 × 0x30 = 14784` 字节，直接返回 false —— **不抛异常、不报错，就是 false**。

而调用方 `bones.cpp` 自己的上限是 `0x10000`，**两个上限互相矛盾，严的那个静默生效**。

**修法**：上限提到 `0x20000`；慢路径从"只拆一次 + 递归"改成循环分块（跨 3 个以上内存区域时会少读）。

**教训**：两个组件各自维护同一约束时，必须有一个是唯一来源。

---

## 第 2 层：选错网格组件

**症状**：骨骼数量 308（正常 60~90），位置全错，转向时乱穿。

**根因**：网格选择是"扫描 actor 偏移 0~0x2000，取骨骼最多的那个"。实测选中：

```
char+0x0118 with 308 bones   ← UCyEntranceEffectsDataAsset（数据资产）
char+0x0458 with  69 bones   ← ACyGameState（游戏状态）
char+0x13E8 with  68 bones   ← 已超出该对象范围
```

**这三个偏移都不是网格组件。** "308 根骨骼"是读数据资产的随机内存后误判出来的。

**修法**：用声明字段 `AWFBaseCharacter::MeshFor3PP @ 0x0EC0`，并加验证。

## 第 3 层：组件判定的类名匹配

**症状**：加了类名校验后，**所有候选都被拒绝** → `no character has bones yet`。

**根因**：我第一版规则是"类名以 `SkeletalMeshComponent` 结尾"。实测运行时类名：

```
char+0x0EC0 -> 'PMSkelMeshComp'              ← 身体网格
char+0x0370 -> 'PMSkelMeshComp'
char+0x0ED8 -> 'PMPaper2DSkeleltalMeshComp'  ← 纸片模式网格
```

C++ 类型是 `UPMSkeletalMeshComponent`，但**运行时 FName 被缩写**成 `PMSkelMeshComp`。

第二版改成"含 `Skel` + 含 `Comp`"，结果又接受了 `SkeletalMesh`（**资产**，不是组件，13 根骨骼），
兜底扫描拿它盖掉了正确的 79 根。

**修法**：**放弃字符串匹配**，改用 UClass 指针比对：

```cpp
ue::FindClassByName("SkeletalMeshComponent")   // 找一次，缓存
ue::IsA(candidate, thatClass)                  // 遍历 SuperStruct 链
```

`IsA` 是纯指针遍历，零引擎调用，子类自动匹配，**不受命名方案影响**。

## 第 4 层：骨名数组步长

**症状**：census 打出的骨名每 3 个槽才有一个是真的：

```
[0] Root                          ← 真
[1] None                          ← 垃圾
[2] neByteProperty?IntProperty    ← 垃圾
[3] Bip001-Spine1                 ← 真
```

**根因**：步长硬编码 16，真实值 **48**。79 根只读到前 26 个位置，且索引全部错位 3 倍。

**为什么旧验证没发现**：它只探测 `entry 0`。第 0 项在任何步长下都是真名，**这个检查不可能失败**。

**修法**：遍历候选步长打分。但**第一次改完仍然选错**（选了 24）——
因为只采样前 24 个槽，24 步长恰好在那段落在真名上。

最终判据改为 **父索引的合法性 + 全数组遍历**，才稳定选出 48。

**教训**：采样窗口必须覆盖到"错误开始出现"的位置，否则短窗口会给出假阳性。

## 第 5 层：父骨索引不可信（当前）

**症状**：步长终于对了（读到完整 41 根真骨名），但骨架画出来是**从头部放射的星芒**。

**根因**：`+0x08` 处的"父索引"不是父索引。原始字节：

```
[0] D1 7D 00 00 00 00 00 00 | FF FF FF FF | 1F AE 7A 01 00 00 00 00
[1] 28 3F 70 01 00 00 00 00 | 01 00 00 00 | 62 F9 5E 01 00 00 00 00
[2] 15 7D 5E 01 00 00 00 00 | 03 00 00 00 | 23 AE 7A 01 00 00 00 00
```

这是 `[8字节值][4字节序号]` 交替，序号是 `-1,1,3,5,7...` 单调递增。
**不是父子关系**，是某种序列号。范围校验能通过（值都合法），但指向错误。

**修法**：不再读这个字段，改用 **UE 变换关系反推父骨**：

```
ComponentSpace[i] = BoneSpace[i] × ComponentSpace[parent[i]]
⇒ ComponentSpace[parent] = BoneSpace[i]⁻¹ × ComponentSpace[i]
```

即：算出父骨**应该**在哪，然后在全部骨骼里找位置最接近的那根。

用引擎自己算好的两个数组，不需要任何字段偏移、不需要骨名，
对**每一根**骨骼都成立（包括名字解析不出来的那些）。

**星芒防护**：错误的父骨集合会表现为"所有骨骼都指向同一个中心"。
所以额外校验：**单根骨骼不能是超过 1/3 骨骼的父节点**，且至少有 4 根骨骼充当父节点。
